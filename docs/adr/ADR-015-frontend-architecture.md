# ADR-015: Frontend Architecture and Phase 12 Scope

**Status:** Accepted

## Context
The Next.js scaffold from Phase 0-2 has had no real UI built on it since —
11 backend phases with nothing demoable on top. This ADR covers the
architecture decisions needed to start building for real, and the scope
this specific phase covers versus what's deliberately deferred.

## Decision 1: client-rendered app within the Next.js App Router, not RSC-heavy
The backend authenticates via bearer JWT in an `Authorization` header, not
cookies (see `TokenResponse` in `app/schemas/auth.py` — both tokens come
back as JSON body fields). React Server Components and Server Actions want
credentials available on the server (typically via cookies); forcing that
shape onto a bearer-token API would mean re-implementing token storage and
refresh server-side for no real benefit at this scale. Pages are client
components (`"use client"`) that call the API directly from the browser;
the App Router is used for routing and layout composition, not data
fetching. A future iteration could move to httpOnly-cookie sessions with a
backend-for-frontend layer if this app grows real production traffic — not
justified for the current scope.

## Decision 2: generated types from the real, live OpenAPI schema, not hand-written
`lib/api/schema.d.ts` is generated by `openapi-typescript` directly against
a running backend's `/openapi.json` (`npx openapi-typescript openapi.json -o
lib/api/schema.d.ts`) — not hand-typed guesses at response shapes that could
silently drift from what the API actually returns. Regenerate this file
whenever a backend schema changes; it is checked in so the frontend builds
without needing a live backend, but it is a generated artifact, not a
source of truth to hand-edit.

A thin typed fetch wrapper (`lib/api/client.ts`) sits on top — handling the
`Authorization` header, JSON parsing, and the app's specific error shape
(`{"error": {"code", "message", "request_id"}}`, see Phase 2/11) — rather
than a fully generated client, so token refresh and error handling stay in
one reviewable place.

## Decision 3: TanStack Query for server state, not hand-rolled `useEffect`/`useState`
Every page needs loading/error/cache/refetch handling for server data
(documents, conversations, agent runs). Hand-rolling this per component is
exactly the kind of repeated, error-prone boilerplate a well-established
library removes — this is a justified dependency addition, not
"unnecessary complexity" (CLAUDE.md §60), because the alternative is
strictly more code and more chances for the same bug (stale closures,
missed loading states) to recur in every component that fetches data.

## Decision 4: tokens in memory + localStorage, with the trade-off stated plainly
The backend returns both access and refresh tokens as JSON (not httpOnly
cookies), so there is no cookie-based option available without backend
changes out of this phase's scope. Tokens are held in a React context for
the current session and mirrored to `localStorage` so a page reload doesn't
force a re-login. This is the standard, real trade-off for a bearer-token
SPA without backend cookie support: vulnerable to token theft via XSS
(mitigated by React's default JSX escaping and not rendering untrusted HTML
anywhere in this app), not vulnerable to CSRF the way a cookie-based session
would be without extra protection. Documented here rather than silently
chosen — a genuine production deployment handling sensitive data would
likely want the backend to move to httpOnly cookies instead.

## Decision 5: design direction — "the reference archive," not a generic AI-product look
The product's actual differentiator is grounded, cited answers — trust
traceable to a real source, not a generic chatbot. The design leans into
that directly rather than defaulting to a templated look:

- **Palette**: cool ink-slate (`#1B2430`) on cool paper-white (`#F7F5F0`,
  deliberately not the warm cream near `#F4F1EA` that reads as a
  Claude-interface tell), with a single narrowly-scoped amber accent
  (`#C9932E`) used *only* for citations and highlighted source text — like
  a highlighter mark in an archive, not a general-purpose brand color.
  Deep forest green (`#3D7A5C`) for confirmations, deep brick (`#B23A34`)
  for destructive/high-risk actions — both closer to the ink register than
  a bright generic alert palette.
- **Type**: Space Grotesk (display/headings — geometric, structured,
  distinct from the ubiquitous Inter), IBM Plex Sans (body — legible,
  quietly technical), IBM Plex Mono (IDs, timestamps, file metadata,
  citation numbers — reinforcing the archival/reference register).
  Deliberately not a serif display face, to avoid even a differently-colored
  variant of the cream+serif default. Self-hosted via `@fontsource/*`
  packages (npm, bundling the actual `.woff2` files) rather than
  `next/font/google` — found during the build-verification pass that this
  sandbox's network allowlist doesn't include `fonts.googleapis.com` (the
  same category of constraint as `huggingface.co` being blocked for
  `sentence-transformers` on the backend). Rather than abandon the type
  choices or ship a build nobody had verified, switched to self-hosted
  font packages: genuinely better practice regardless of the sandbox
  constraint (no runtime dependency on Google's font CDN, one fewer
  third-party request per visitor), verified with a real, clean production
  build in this environment, not just assumed to work.
- **Signature element**: citation references in chat answers aren't small
  bracketed numbers — they're interactive reference chips that expand
  inline to show the actual highlighted source excerpt and originating
  document, styled like pulling a card from an archive. This is the one
  place the design takes a real risk, and it's tied directly to the
  product's actual value proposition, not decorative.
- Layout (persistent sidebar + main content) is a standard app shell
  because this is a working productivity tool, not a marketing page — the
  frontend-design skill's "avoid templated defaults" guidance is about
  avoiding unearned genericness, not about avoiding conventional structure
  where convention is actually the right call.

## Decision 6: Phase 12 scope — the core RAG loop, not the whole product
Given the size of a full enterprise frontend, this phase covers a genuinely
complete, demoable slice: authentication (register/login/logout), document
management (upload/list/delete), and the chat/RAG interface with real
citations. **Deliberately deferred, not silently dropped:**
- Agent run UI + human-approval workflow — a genuinely complex interaction
  (pausing mid-run, a real approve/reject decision with consequences)
  that deserves its own focused phase rather than being squeezed in here.
- Admin/evaluation dashboards, collection management, member/role
  management UI.

These are tracked in PLAN.md as explicit next-phase candidates, the same
way every other phase's deferred scope has been tracked throughout this
project.

## Consequences
- `frontend/openapi.json` and `frontend/lib/api/schema.d.ts` are both
  checked in — the former as the exact snapshot the latter was generated
  from, useful for diffing when the backend schema changes.
- Components fetch through a small set of typed query/mutation hooks in
  `lib/api/hooks.ts`, not raw `fetch` calls scattered through pages —
  keeping the real backend contract (from generated types) as the only
  source of truth for what a response looks like.
